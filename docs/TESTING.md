# Проверки

## Проверки выпуска rc.9

Rc.9 добавляет перенос аккаунтов и проверки отзыва доступа после смены
владельца. В публичный комплект включены четыре synthetic runtime suites:
перенос/откат и согласие получателя, команды и кнопки ботов с durable replay,
продолжение relay по прежним ID и гонки доступа к маршрутам.

Новые сценарии используют временную модель БД и перехваченные provider-вызовы;
они не читают рабочую конфигурацию и не отправляют сообщения. Targeted
проверка новых suites и portable-runtime — **87/87 PASS** на Windows.
Полный прогон экспортированного runtime: **182 PASS, 1 SKIP**, отказов нет.
Package suite: **11 PASS, 1 SKIP**. Пропуски относятся к POSIX/symlink
возможностям Windows. Targeted и полные наборы пересекаются и не суммируются.
Проверены allowlist, согласованность lockfile, отсутствие секретов,
детерминированность архива и manifest распаковки. Ранее исправлен DOM mock для meta base path;
поведение лендинга этим исправлением не менялось.

Новая чистая установка rc.9 и реальная отправка Telegram/МАКС не выполнялись.
Результаты Linux, VPS, браузера и reboot предыдущих выпусков ниже относятся
только к тем выпускам; переносить их в приёмку rc.9 нельзя. Выпуск prerelease.

## Выпуск rc.7: продолжение после отказов

Предварительный выпуск **0.1.0-rc.7** исправляет независимое продление собственных сертификатов
и проверку текущего задания домена после потери ответа. Ошибка старого адреса
не отменяет попытки для остальных сертификатов. Небезопасные конфигурации
не передаются Certbot; после остальных попыток возвращается безопасная общая
ошибка. В обоих установщиках `NEEDRESTART_MODE=l` запрещает автоматические
перезапуски со стороны `needrestart`. Собственные post-install действия пакетов
этим не отключаются. Оба установщика завершают группу дочерних процессов
команды при ошибке или таймауте. В CLI bootstrap обоих проектов обработчики
`SIGTERM`/`SIGHUP` завершают дочерние процессы и освобождают общую блокировку,
возвращая `BOOTSTRAP_INTERRUPTED`.

Финальная приёмка: **44/44 Linux suites**, включая 6 групп обоих порядков с
настоящим изолированным nginx. В каждом пакете прошли 8 проверок процессов,
окружения и отмены, 7 проверок продления. Chrome: GitPosted **48/48**,
GitRePosted **67/67**. Изолированные HTTP/PHP/Unix-socket/MySQL сценарии
GitPosted — **6/6**, без реального API платформ. Новые регрессии сначала
показали ошибки в rc.6; после исправления они прошли.

На существующей тестовой паре hashes конфигурации и состояния, PID приложений
и общих служб сохранились. HTTPS обоих проектов, nginx test, схема GitPosted
33/MAX5 и собственный renewal новым helper подтверждены; временные БД/users
удалены. Это проверка исправлений, а не новая установка: две свежие rc.7
на чистых VPS в обоих порядках отдельно не выполнялись. Прежние результаты
rc.6 ниже исторические; числа пересекаются и не суммируются в уникальные тесты.

Регрессии продления запускаются без реального Certbot:

```bash
python3 -B tests/deep-coinstall-nginx-test.py
```

Для приёмки проверьте отказ старого и действующего адреса по отдельности,
продолжение обработки остальных собственных сертификатов, отказ небезопасного
пути и отсутствие секретов в общей ошибке. Отдельно проверяются завершение
дочерних процессов GitPosted при таймауте, сохранность PID первого приложения
при работе `needrestart` и потеря ответа нового задания домена при наличии
прежнего завершённого задания. Для `SIGTERM` и `SIGHUP` нужна отдельная реальная
Linux-проверка отсутствия отложенной записи дочернего процесса после выхода
bootstrap и возможности вновь взять общую блокировку.

Прерванное добавление пакета вторым установщиком должно безопасно остановиться
при `iU`, `iF` или ожидающих triggers: требуется отдельная проверка APT/dpkg
оператором и обслуживание, затем продолжение той же установки. Общий
`dpkg --configure --pending` для исправления всего shared-сервера автоматически
не запускается. Принудительный `SIGKILL` и потеря питания требуют ручной проверки
дочерних процессов, пакетов, nginx и сохранённого задания перед `--resume`;
обычные fixtures не подтверждают восстановление после любого сбоя питания.

## Выпуск rc.6: два проекта на одном сервере

Rc.6 добавляет последовательную установку GitRePosted и GitPosted в любом
порядке. Первый проект должен завершить свой мастер; второй получает отдельный
домен или поддомен через `--host` и использует проверенный общий стек.
Сторонние сайты и произвольный существующий MySQL в этот сценарий не входят.

Пройдены Linux suites обоих установщиков — **40/40**. В них входят 6 групп
перекрёстной проверки с настоящим изолированным nginx: оба порядка установки,
имена сайтов, HTTP-01, общая блокировка, отказ сертификата и сохранность
первого проекта. Chrome fixtures: GitPosted — **40/40**, GitRePosted — **59/59**.
Отдельные изолированные проверки GitPosted с настоящими PHP/HTTP/Unix-socket
и MySQL — **6/6**. Результаты пересекаются и не суммируются в число уникальных
сценариев.

На реальной тестовой VPS уже работал GitRePosted rc.4. GitPosted rc.6
установлен вторым с отдельным DNS-именем. Старому rc.4 не хватало
`php8.3-mysql` и `unzip`: эти пакеты подготовили явным отдельным обслуживанием
без обновления или удаления остальных пакетов. После этого прошли настоящий
мастер GitPosted, вход в админку и закрытие мастера. Схема GitPosted —
33 таблицы/MAX version 5, GitRePosted — 19 таблиц. Конфигурация, состояние
и nginx-файл первого проекта сохранили SHA-256, PID его bridge и MySQL
не изменились, количество записей в первой базе сохранено.

HTTPS, запуск продления только собственных сертификатов и certbot dry-run —
PASS. В команде продления добавлен `--no-random-sleep-on-renew`, поскольку
случайный сдвиг уже задаётся systemd timer и лишняя пауза мешала конечному
таймауту проверки.

Оба бота в этой реальной установке пропущены. Реальные webhook и доставка
не проверялись. Оба порядка с двумя свежими rc.6 на настоящем VPS отдельно
не проверены: оба порядка подтверждены изолированными Linux-проверками.

Локальные команды новых контрактов:

```bash
python3 -B tests/coinstall-provision-test.py
python3 -B tests/coinstall-broker-test.py
```

Fixtures должны проверять оба порядка, поддельное/незавершённое состояние
соседа, занятые имена, отдельные server_name и единственного default_server,
общую блокировку, продолжение после отказа, HTTP-01 до появления сертификата
и сохранение первого проекта. При тестировании nginx используйте изолированный
конфиг, временные сертификаты/каталоги и loopback-порты; рабочую конфигурацию
сервера ради отрицательного теста не повреждайте.

Для следующей приёмки отдельно запишите версии обоих пакетов, порядок,
состояние первого проекта
до/после второго, результат браузерных мастеров, HTTPS и продления, отказов и
`--resume`. Fake transports не подтверждают доставку в Telegram или МАКС;
реальные тесты выполняются только с разрешением и выбранными каналами.

Ранее установленный rc.4 и проверки rc.5 ниже — исторические результаты.
Повторный загрузчик на завершённой установке не обновляет её автоматически
и не считается новой совместной установкой rc.6.

## Кандидат rc.5: ссылка в открытом мастере

В rc.4 подтверждён отдельный сбой: если `/install/` уже открыт, переход по
персональной ссылке с тем же адресом и новой частью `#setup=…` не перезапускает
инициализацию страницы. Авторизация мастера не начинается. Обычное открытие
персональной ссылки в новой странице работает; сбой не означает неудачу
bootstrap и не запускает установку повторно.

В rc.5 ссылка обрабатывается и в уже открытой вкладке: её код удаляется из
адреса до запросов, вход запускается после проверки HTTPS и состояния сервера.
Десять новых Chrome fixtures проверяют обычный переход, повторную ссылку во
время входа, сохранение заполненных полей, истёкшую сессию, активное задание,
некорректную ссылку, HTTP, обычный #main, завершённую установку и отказ очистки
адреса. На прежнем rc.4 воспроизведены восемь отказов девятью исходными новыми
тестами; обычный #main работал. Пять UI/browser suites — 59/59 PASS (включая targeted 43/43),
независимый review — PASS. Все запросы перехвачены, реальный enrollment и
платформы не вызываются.

Отдельная чистая установка rc.5 не выполнена. Завершённую rc.4 нельзя вновь
открывать удалением installed marker: автоматического updater здесь нет.
Проверка загрузчика rc.5 с --resume на завершённой системе является проверкой
совместимости с terminal state, а не установкой или обновлением runtime.
Результаты чистой rc.4 ниже не считаются новой чистой установкой rc.5.

## Предыдущий аудит rc.4

Следующие проверки выполнены до повторной очистки VPS. Проверка правок на
уже настроенной системе описана отдельно от чистой установки rc.4 выше.

Повторный аудит направлен на ошибки после потери ответа, отключения питания
и прерывания системных пакетов. Подтверждённые исправления:

- Отсутствующий флаг JSON больше не включает workers или платформу по умолчанию;
  проверены все четыре флага до SQL, HTTP, timers и provider calls.
- Запись конфигурации подтверждает POSIX-каталог после rename. Ошибка на этом
  этапе возвращает неопределённый результат записи; память сверяется с файлом,
  старые credentials отзываются. Неудачное чтение закрывает admin auth.
- Сохранение Node/npm подтверждает файлы и каталоги до отметки готовности;
  сохранённый mysql2 проверяется от UID приложения без соединения с БД.
- `--resume` завершает прерванный dpkg с ограниченным ожиданием блокировок;
  lock-файлы и существующие пакеты не удаляются.
- Потерянный ответ правки настроек или домена сверяется с terminal job.
  Введённые значения сохраняются; автоматического повторного запроса нет.
- Первоначальное меню МАКС подтверждается чтением `/me`: ответ изменения может
  не содержать `commands`. Проверены пустой успешный ответ, потерянный ответ,
  временно недоступное чтение, неверные и дублирующиеся команды. Прежняя
  подписка остаётся до подтверждения новой настройки. Контракт:
  [PATCH /me/commands](https://dev.max.ru/docs-api/methods/PATCH/me/commands),
  [GET /me](https://dev.max.ru/docs-api/methods/GET/me).
- Переход между выпусками при продолжении допускается только на раннем
  bootstrap до мастера/config/DB приложения и при остановленной службе;
  прежний runtime сохраняется. Активная или уже настроенная система отклоняется.

На Windows полный private Node suite: 132 tests, 131 PASS, один прежний
symlink permission skip. Проверка синтаксиса и dependency audit пройдены;
уязвимостей зависимостей не найдено. Пять UI/browser suites: 49/49 PASS.
Два новых browser сценария воспроизвели ошибку на неизменённом rc.3 и прошли
после исправления. Сбои диска и APT проверяются изолированными fixtures;
рабочий сервер и его системные пакеты ради теста не повреждаются.

На Ubuntu прошли 15 suites. После последней правки повторно выполнены все
девять Python suites: provisioning audit/base/Node/machine/cleanup/package —
29/20/19/4/8/12 (92 проверки), broker base/review/node — 16/3/4, без skips.
Четыре PHP suites: application 14 groups, wizard 20, audit и URL consent — PASS.
Public Node runtime — 101/101, UI static — 19/19. Результаты разных suites
пересекаются и не складываются в число уникальных сценариев.

Проверка настоящего установленного mysql2 выявила дополнительную ошибку
кандидата: Node `-e` наследовал закрытый cwd root и отказывался читать package
configuration. Эта версия не публиковалась. Исправленный запуск использует
проверенный доступный source как cwd. Новый Linux fixture с private `0700`
caller повторяет прежний отказ и подтверждает app UID/новый cwd. На фактической
VPS проверены cached Node, app-UID exports mysql2 и реальные file/directory
fsync без подключения к БД из probe. Проверка exports не заменяет полную
криптографическую сверку каждого установленного npm-файла.

Кандидат rc.4 установлен на существующую тестовую систему под общей блокировкой;
два runtime-файла заменены атомарно с проверкой синтаксиса. Config bytes
сохранились, schema verify подтвердил 19 таблиц, доверенный HTTPS health — 200.
Installed marker и active release directory остаются историческими rc.2;
это проверка исправлений, а не автоматическое обновление или новая чистая
установка rc.4. Реальные webhook и отправки по-прежнему не выполнялись.

После deploy настоящий Chrome проверил 30 условий: два входа, ровно одно
сохранение прежнего public URL (200, значения платформ не изменились, PID тот
же), один restart (202, новый PID, старая сессия 401), logout и закрытый мастер.
Ошибок страницы и неожиданных запросов — ноль. Временная недоступность health
при restart восстановилась. Тест не менял пароль и не подключал ботов.

## Дополнительный анализ rc.3

Проверены прерывание сохранения полного пакета, восстановление завершённого
мастера, отказы start/revise/host, потерянные ответы и подключение ботов после
первоначального пропуска. Исправлены четыре подтверждённых дефекта:

- Пакет теперь публикуется целиком из защищённого staging-каталога через
  атомарное переименование; до подтверждения записи каталога на диск
  прежний комплект не удаляется. Проверены ошибки fsync до и после замены.
- Завершённый мастер отключает временную службу даже после сбоя восстановления
  метаданных и не открывает новый socket.
- Однозначный отказ при корректировке настроек показывает новую причину;
  потерянный ответ по-прежнему сверяется с сервером без повторного запуска.
- Позднее подключённые боты получают и проверяют меню `/start`; потерянный
  ответ о настройке меню сверяется чтением состояния платформы.

На Windows полный private runtime suite: 129 tests, 128 PASS, один прежний
symlink permission skip. Dependency audit: 0 vulnerabilities. Контроль
прерываний использует изолированные fixtures, а не остановку рабочей установки.

На фактической Ubuntu прошли 15 suites без ошибок: шесть provisioning families
— 79 проверок, broker base/review/node — 16/3/4, четыре PHP suites, public Node
runtime — 98/98 и UI static — 19/19. Проверки POSIX/root не пропускались.
Отдельно в изолированном Linux-каталоге дважды опубликован настоящий полный
пакет из 83 файлов: первая публикация и атомарная замена, проверка manifest,
нового inode каталога и удаления только прежнего принадлежащего пакета.
Пять UI/browser suites с перехваченными запросами: 43/43 PASS.

Кандидат rc.3 атомарно установлен на уже настроенную тестовую VPS под общей
блокировкой. Конфигурация побайтно сохранилась, schema verify подтвердил
19 таблиц. Это проверка исправлений на существующей тестовой установке,

restart 202, новый PID, отзыв старой сессии, повторный вход и выход; мастер

Оба бота по-прежнему отключены; реальные provider E2E не выполнялись.

## Проверка реальной Ubuntu в rc.2

Комплект **0.1.0-rc.2** подготовлен к публикации после проверки исправления
на Ubuntu Server 24.04. Это prerelease. Реальные боты и доставка публикаций
Telegram/МАКС пока не проверены; обе платформы при live-установке пропущены.

Первая установка опубликованного rc.1 на чистом Ubuntu Server 24.04 выявила
блокер: `npm ci` завершился кодом **126**, так как пользователь приложения
не мог запустить `/opt/gitreposted-node/current/bin/node` (`Permission denied`).
При распаковке vendor archive через Python `tarfile` с `filter='data'` и
`umask 077` каталоги остались с правами `0700`. Бинарный Node имел `0755`, но
этого недостаточно без права прохода по родительским каталогам. Это реальный
сбой установки, который прежние offline suites не обнаружили.

Исправленный полный комплект rc.2 успешно продолжил ту же незавершённую

Runtime suites используют Node built-ins и временные fixtures: форматирование,
media splitting, streaming, idempotency, lease heartbeat, auth и rate limits.
Module suites не запускают сервер. portable-server запускает копию настоящего
entrypoint в временном каталоге с fake MySQL и запрещённым provider fetch;
HTTP-запросы идут только на loopback. Он проверяет CLI schema contract,
авторизацию, смену пароля, durable enqueue и подключение платформ после
установки. Эти проверки не читают рабочую конфигурацию, не меняют реальные
webhook и не отправляют публикации. Python package tests проверяют детерминированность,
manifest, allowlist, секреты, symlink и защиту чужих файлов при экспорте.
Остальные suites тестируют соответствующий компонент через fixtures; их
наличие не заменяет выполнения. Для Node runtime установка зависимостей
проводится только через `npm ci --omit=dev` по package-lock.json.

## Browser suites

Для браузерных fixtures нужен Playwright с Chromium. Это dev-инструмент;
он не входит в dependencies приложения и не нужен работающему боту. На Linux
установите его в отдельный временный или developer-каталог вне checkout:

```bash
GITREPOSTED_DEV_DIR="$(mktemp -d -t gitreposted-browser-dev.XXXXXXXX)"
npm install --prefix "$GITREPOSTED_DEV_DIR" --no-save --package-lock=false playwright
"$GITREPOSTED_DEV_DIR/node_modules/.bin/playwright" install chromium
export NODE_PATH="$GITREPOSTED_DEV_DIR/node_modules"
node --test tests/ui-browser.test.cjs tests/wizard-audit-ui.test.cjs tests/deep-wizard-ui.test.cjs
```

Node.js, npm и системные зависимости Chromium должны быть доступны в среде
разработки. Системные библиотеки браузера при необходимости подготавливаются
отдельно администратором; не запускайте installer ради подготовки dev-среды.
Вместо NODE_PATH можно задать `PLAYWRIGHT_MODULE` абсолютным путём к модулю
Playwright. Если Chromium уже установлен, `UI_BROWSER_EXECUTABLE` задаёт путь
к его исполняемому файлу Chrome/Chromium; иначе Playwright использует скачанный
браузер. Не задавайте DEEP_WIZARD_SCRIPT для штатной проверки комплекта:
это необязательный override отдельного script fixture. Browser suites
перехватывают все запросы и не обращаются к bot API.

Сборка и проверка распакованного архива:

```bash
python3 -B scripts/build.py --output ../release-artifacts
tar -xzf ../release-artifacts/gitreposted-installer.tar.gz -C ../verification
python3 -B scripts/build.py --verify-manifest ../verification/gitreposted-installer
```

Каталог `../verification` создайте заранее. Артефакты и распаковка должны
находиться вне исходников. Не запускайте bootstrap или provision на рабочей
машине ради unit-теста: эти команды меняют систему.

Контрольный сценарий свежей VPS: установка по полному выпуску, HTTPS по IP и
домену, выключенные платформы, Telegram-only, MAX-only, обе платформы, restart
на каждом этапе мастера, вход/выход/смена пароля, закрытие `/install/`, свежая
схема, включение workers только в конце, передача текста/фото/альбома,
проверка прав на чужие каналы, обратное эхо и неопределённый provider response.
Реальные публикации выполняются только с разрешения владельца и в названные
тестовые каналы. Нельзя для этого запускать копию production-очереди.
