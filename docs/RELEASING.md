# Сборка и выпуск

Текущий предварительный выпуск — **0.1.0-rc.8**. Rc.1–rc.7 уже
опубликованы; их tags и assets неизменяемы. Не пересобирайте и не заменяйте
старые архивы исправленным кодом. Фактические проверки каждого выпуска
описаны отдельно в [TESTING.md](TESTING.md).

## Выпуск rc.8

Новые установки GitPosted и GitRePosted работают под фиксированными путями
`/GitPosted` и `/GitRePosted` на общем IP, общем домене или разных доменах.
Мастер и админка находятся под путём своего приложения: например,
`/GitRePosted/install/` и `/GitRePosted/control/`. Второй установщик без
`--host` наследует проверенный текущий `site_host` первого проекта. Базы,
конфигурация, пользователи, данные, службы и cookies приложений раздельные.
Общий nginx направляет запросы в нужное приложение; для одного адреса есть
один владелец сертификата — первый установщик на этом адресе. Его продление
работает независимо от незавершённого этапа соседнего установщика.

Существующие установки rc.7 и ниже с приложением в корне адреса сохраняют
свою раскладку. Второму проекту рядом с проверенной старой установкой нужно
явно указать другое DNS-имя. Автоматического переноса или обновления готовой
установки нет: повторный loader и `--resume` её не обновляют.

На очищенной Ubuntu Server 24.04 проверен порядок GitPosted → GitRePosted
на общем IP: bootstrap занял 113 и 29 секунд. Найденную в первом кандидате
ошибку 404 мастера исправили до успешного завершения обоих мастеров. Затем
на снова очищенной системе окончательные пакеты прошли обратный порядок
GitRePosted → GitPosted за 124 и 34 секунды без исправлений на сервере и без
`--resume`. Оба мастера, входы в панели, сохранность первого приложения,
раздельные cookies и выходы проверены, в том числе после реальной перезагрузки.
Общий сертификат и certbot renew dry-run также проверены. Доменные варианты
проверены с настоящим изолированным nginx; эти VPS-прогоны использовали общий IP.

Автоматические результаты: Linux **53/53 suites**, PHP lint и Bash syntax;
browser fixtures GitPosted **57/57** и GitRePosted **68/68**; дополнительные
Node prefix/HTTP проверки GitRePosted **11/11**; изолированные
HTTP/PHP/Unix/MySQL сценарии GitPosted **6/6**. Эти наборы пересекаются,
их нельзя складывать в число уникальных сценариев. В фактической приёмке
на VPS обе платформы пропущены: реальная отправка в Telegram и МАКС здесь
не проверялась. Полная запись и ограничения — в
[TESTING.md](TESTING.md#проверки-выпуска-rc8).

При следующем выпуске повторяйте оба порядка и проверяйте общий IP, общий
домен, разные домены, совместимость со старой корневой установкой, занятый
адрес, незавершённый первый мастер, общую блокировку, отказ и продолжение,
HTTP-01 и продление только собственных сертификатов. Общий модуль coinstall
должен совпадать в обоих пакетах. Подтверждайте сохранность первой
конфигурации, базы и служб; установка второго проекта не должна обновлять
общий стек как побочный эффект.

## История: rc.7

Rc.7 исправляет продолжение продления собственных сертификатов после ошибки
одного адреса и обработку потерянного ответа задания домена. Оба установщика
задают `NEEDRESTART_MODE=l`, чтобы `needrestart` сам не перезапускал службы.
Это не отменяет post-install скрипты пакетов и защиту общего стека. В GitPosted
дополнительно исправлено завершение дочерних процессов команд при отказе
или таймауте. CLI bootstrap обоих проектов обрабатывает `SIGTERM`/`SIGHUP`
с очисткой дочерних процессов и кодом `BOOTSTRAP_INTERRUPTED`.
Незавершённые пакеты второй установки требуют явной отдельной
проверки и обслуживания; автоматического общего исправления dpkg нет.

Для rc.7 прошли 44/44 Linux suites, Chrome GP48/48 и GRP67/67, изолированные
HTTP/PHP/Unix/MySQL сценарии GP6/6. Результаты и оставшиеся ограничения записаны
в [TESTING.md](TESTING.md#выпуск-rc7-продолжение-после-отказов).
Не переносите числа или факты реальной установки rc.6 в отчёт rc.7. Проверьте
новые fixtures продления, дочерних процессов, пакетных прерываний и потерянного
ответа мастера; принудительный `SIGKILL` требует отдельного аудита состояния.

## История: rc.6

Rc.6 добавил совместное размещение GitRePosted и GitPosted в любом порядке.
Первый установщик готовит чистый Ubuntu Server 24.04; второй принимает только
проверенное завершённое состояние соседнего проекта и отдельное DNS-имя
через `--host`. Общие nginx/MySQL/PHP используются совместно, приложение,
база, пользователи, секреты и фоновые задачи остаются раздельными.
Защита от посторонних сайтов и неизвестного состояния сохраняется.

Для rc.6 прошли Linux suites **40/40**, Chrome fixtures GitPosted **40/40**
и GitRePosted **59/59**, изолированные PHP/HTTP/Unix/MySQL проверки GitPosted
**6/6**. Оба порядка включены в 6 групп с настоящим изолированным nginx.
На настоящем VPS GitPosted rc.6 установлен вторым рядом с готовым GitRePosted
rc.4: сохранность первого проекта, мастер/админка второго и HTTPS подтверждены.
Это не две свежие rc.6 в обоих порядках на VPS; реальные публикации здесь
не выполнялись. Полная запись приёмки — в [TESTING.md](TESTING.md).

Результаты rc.7 и ниже относятся к указанным прежним выпускам и не заменяют
отдельную запись приёмки rc.8 в TESTING.md.

## История: rc.4 и rc.5

Опубликованный rc.4 прошёл новую непрерывную установку на чистом Ubuntu
Server 24.04 публичной командой, без `--resume`: bootstrap — 131 секунда,
мастер — 27/27, настройки и перезапуск админки — 30/30, смена пароля — 27/27.
Оба бота пропущены; реальная доставка по платформам ещё не подтверждена.

Rc.5 исправляет переход по персональной ссылке, когда мастер уже открыт и
меняется только часть адреса после `#`. Десять новых browser fixtures покрывают
повторную ссылку, истёкшую сессию, сохранность формы, активное задание и отказы
без повторного enrollment. Пять UI/browser suites — 59/59 PASS, независимый
review — PASS. Все 28 runtime-файлов совпадают с опубликованным rc.4; изменение
относится к мастеру и его тестам, а не к приложению.

Отдельная чистая установка rc.5 не выполнена. Завершённая тестовая система
остаётся rc.4: запуск нового loader с --resume на ней проверяет сохранность
terminal state и не обновляет installer/runtime. Результаты реального reboot
и renewal в TESTING.md относятся к новой чистой rc.4. Для rc.5 собирается
собственный архив; прежние assets не заменяются.

## Подготовка публичного комплекта

Публичный комплект создаётся из проверенных исходников по точному списку
scripts/build.py. Экспорт не выполняет Git-команды, не создаёт репозиторий и
не публикует данные. Installer source не обязан содержать вторую копию
runtime: maintainer явно передаёт authoritative application directory.

```bash
python3 -B scripts/export.py --runtime-source /path/to/reviewed-application --destination /path/to/generated-checkout
```

Входной каталог runtime должен содержать только ожидаемые application targets;
экспорт читает исключительно перечисленные имена. Реальные env, DB, sessions,
серверные конфиги, история, logs и private инструкции не читаются и не
копируются. LICENSE публичного комплекта должен быть заранее сверенным MIT
оригиналом. Новые файлы добавляются в allowlist после проверки.

Exporter выполняет ограниченные изменения distribution metadata: добавляет
`license: MIT` в package.json и корневую запись package-lock.json, а также
меняет npm test на `node --test ../../tests/runtime/*.test.mjs`. Это позволяет
запускать включённые offline suites из payload/src. Версии зависимостей,
resolved URLs и integrity не меняются; authoritative application не правится.
Repository/homepage/issues metadata указывает на фактически созданный
`https://github.com/SergeyFromMariupol/GitRePosted`.
Text files нормализуются в LF в соответствии с .gitattributes; бинарные assets
не меняются. Исходные файлы при этом остаются на месте с исходными байтами.

Первый destination должен быть пустым. Допускается существующая обычная `.git`
директория; её содержимое не просматривается и не изменяется. Экспорт создаёт
собственный marker с SHA256 каждого принадлежащего ему файла. Последующий
экспорт откажется при чужом файле или ручной правке. Не удаляйте marker и не
перезаписывайте чужие изменения ради обхода проверки. `install.sh` может быть
добавлен отдельно как зафиксированный release loader; exporter его сохраняет.

Из generated checkout выполните проверки в TESTING.md, затем:

```bash
python3 -B scripts/build.py --output /path/to/release-artifacts
```

Для maintainer также поддерживается сборка непосредственно из installer
source с явным `--runtime-source /path/to/reviewed-application`. Команда
проверяет каждый файл, строит детерминированный tar.gz и внешний SHA256.
Распакуйте в отдельный пустой каталог и выполните `--verify-manifest`.
Два запуска при одинаковых байтах исходников должны дать одинаковый SHA256.

Перед публикацией подтвердите: allowlist проверен; examples содержат только
общие пути и placeholders; lockfile согласован; Node/PHP/Python suites прошли;
фактический сценарий установки и оставшиеся ограничения отражены в docs.
У rc.1 подтверждён блокер на чистом Ubuntu; его исправление rc.2 проверено
продолжением установки, а опубликованный rc.4 — отдельным запуском с нуля.
Для rc.6, rc.7 и rc.8 результаты зафиксированы отдельными записями в TESTING.md.
Предыдущие проверки не заменяют приёмку нового комплекта. Выпуск остаётся
prerelease: перед stable нужны проверка актуального комплекта с нуля и
реальные тестовые каналы обеих платформ; offline-тесты не заменяют эти результаты.

Публикация GitHub — отдельное действие. Сначала создайте настоящий repository,
проверьте URL и permissions. Затем опубликуйте соответствующий tag, архив и
checksum. Подставьте фактический HTTPS asset URL и SHA256 в копию
scripts/release-loader.sh; шаблон с placeholders запускаться не должен.
`install.sh` не входит в архив, поэтому его pin не создаёт циклический hash.
Проверенную curl-команду добавляют в README только после проверки реальных
ссылок. Не меняйте assets уже выпущенного tag незаметно для пользователей.

Изменение рабочего VERSION не меняет опубликованный loader. Выпуски используют
два commit: исходный tag содержит комплект без корневого
install.sh, затем отдельный commit main добавляет loader с проверенным URL/hash
новых assets. Старый loader не должен попадать в исходный tag нового выпуска.
История предыдущего commit и assets сохраняется; force-push не нужен.
После публикации необходимо анонимно проверить новый loader, архив и checksum.
